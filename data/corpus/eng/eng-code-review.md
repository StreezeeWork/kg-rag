# Правила code review

## 1. Зачем нужен code review

Code review — обязательный этап перед слиянием любого изменения в репозиториях GitLab (gitlab.nimbus.local). Ревью нужно не для поиска виноватых, а для того, чтобы знания о коде были как минимум у двух человек, а дефекты находились до production. Правила действуют для всех команд разработки «Нимбус.Маршрут» и «Нимбус.Пэй», включая подрядчиков с доступом к GitLab.

## 2. Апрувы и права на слияние

- Merge request (MR) можно влить только после 2 апрувов от инженеров, которые не являются авторами изменений.
- Один из апрувов обязательно даёт владелец кода, указанный в файле CODEOWNERS репозитория.
- Для репозиториев платёжного ядра «Нимбус.Пэй» требуется 3 апрува, один из которых — от инженера группы безопасности платежей.
- Апрув автоматически сбрасывается, если после него в MR добавлен новый коммит с изменением кода.
- Кнопку Merge нажимает автор MR после получения всех апрувов и зелёного пайплайна; ревьюер не сливает MR за автора.

## 3. Сроки ревью (SLA)

Ревьюер назначается ботом по файлу CODEOWNERS в момент, когда MR выходит из статуса Draft. Первая реакция ревьюера — комментарий или апрув — должна появиться не позднее 4 рабочих часов с момента назначения. Полное ревью MR стандартного размера завершается в течение 1 рабочего дня. Если по MR нет реакции 2 рабочих дня, бот публикует напоминание в канале команды в «Волне» и переназначает ревью на тимлида. Срочные исправления для инцидентов SEV1 и SEV2 ревьюируются вне очереди: допускается 1 апрув с обязательным полным ревью в течение следующего рабочего дня.

## 4. Размер merge request

Маленькие MR ревьюят быстрее и внимательнее, поэтому размер ограничен. Рекомендуемый размер MR — не более 400 изменённых строк без учёта сгенерированного кода и lock-файлов. MR больше 800 строк бот помечает меткой size/XL, и такой MR нужно разбить на части или объяснить в описании, почему это невозможно. Один MR решает одну задачу из «Орбиты», ключ задачи указывается в заголовке. Описание MR заполняется по шаблону: что изменено, зачем, как проверено, есть ли миграции базы данных и feature flags.

## 5. Что проверяет ревьюер

1. Корректность: код делает то, что заявлено в задаче, обработаны граничные случаи и ошибки.
2. Тесты: новая логика покрыта тестами, а тесты проверяют поведение, а не реализацию.
3. Безопасность: в коде нет секретов, входные данные валидируются, SQL-запросы параметризованы.
4. Обратная совместимость: миграции и изменения API не ломают работающие версии клиентов.
5. Читаемость: понятные имена, нет дублирования, комментарии объясняют «зачем», а не «что».
6. Наблюдаемость: для новой функциональности добавлены логи и метрики.

Комментарии ревьюера помечаются префиксами: blocker — без исправления сливать нельзя, question — нужен ответ автора, nit — мелкое замечание на усмотрение автора. Ревьюер не проверяет форматирование вручную: его контролирует линтер в CI.

## 6. Конфликты мнений

Если автор и ревьюер не пришли к согласию за 2 раунда комментариев, они обсуждают вопрос голосом в созвоне длительностью до 15 минут. Если договориться всё равно не удалось, окончательное решение принимает техлид команды-владельца кода. Разногласия по архитектуре — выбор хранилища, появление нового сервиса или формат API — выносятся на архитектурный комитет по правилам оформления ADR. Итог обсуждения фиксируется комментарием в MR, чтобы следующий читатель понимал, почему выбран именно этот вариант.
