# Ветвление и оформление коммитов

## 1. Модель ветвления: trunk-based development

Все продуктовые репозитории в GitLab работают по модели trunk-based development. Единственная долгоживущая ветка — main, из неё собираются все релизы. Рабочие ветки короткоживущие: ветка должна быть влита в main не позднее 3 рабочих дней после создания. Незавершённую функциональность сливают в main за выключенным feature flag, а не держат в отдельной ветке неделями. Долгоживущие ветки вида develop или release-candidate в новых репозиториях не создаются.

## 2. Именование веток

Имя ветки строится по шаблону тип/ключ-задачи-краткое-описание, где ключ задачи берётся из трекера «Орбита». Пример правильного имени: feat/ORB-2417-route-cache. Допустимые типы веток: feat, fix, refactor, chore, docs и hotfix. Описание пишется латиницей в нижнем регистре через дефис, а длина имени ветки — не более 60 символов. Ветки, в которых нет новых коммитов 30 дней, бот удаляет автоматически, предварительно предупредив автора в «Волне» за 7 дней.

## 3. Оформление коммитов (Conventional Commits)

Сообщения коммитов оформляются по спецификации Conventional Commits в виде тип(область): краткое описание. Пример: fix(billing): учитывать часовой пояс клиента при расчёте счёта. Правила:

- заголовок коммита не длиннее 72 символов и без точки в конце;
- тело коммита отделяется пустой строкой и объясняет, зачем сделано изменение;
- в футере указывается ключ задачи, например Refs: ORB-2417;
- несовместимые изменения API помечаются восклицательным знаком после типа и строкой BREAKING CHANGE в футере.

По типам коммитов автоматически формируется changelog, поэтому неверный тип приводит к ошибке в release notes. Формат проверяет commitlint в пайплайне: MR с неправильным заголовком не проходит этап lint.

## 4. Слияние в main

MR вливается в main методом squash merge, поэтому в истории main остаётся один коммит на задачу с сообщением из заголовка MR. Отсюда правило: заголовок MR тоже должен соответствовать Conventional Commits. Перед слиянием ветка обновляется через rebase на актуальный main; merge-коммиты из main в рабочую ветку не допускаются. История main остаётся линейной, что упрощает git bisect и откат отдельных изменений.

## 5. Защита ветки main

- Прямой push в main запрещён всем ролям, включая Maintainer и администраторов GitLab.
- Force push в main и удаление ветки main заблокированы настройкой Protected branches.
- Слияние возможно только через MR с успешным пайплайном и апрувами по правилам code review.
- В репозиториях «Нимбус.Пэй» каждый коммит должен быть подписан SSH-ключом, зарегистрированным в профиле GitLab, а неподписанные коммиты отклоняются push-правилом.
- Изменить настройки защиты ветки может только группа platform-admins по заявке в «Помощнике».

## 6. Частые ошибки

Самая частая ошибка новичков — одна ветка на несколько задач: такой MR трудно ревьюить и невозможно откатить по частям. Вторая — коммиты с сообщениями вроде «fix» или «wip» в итоговой истории; перед открытием MR их нужно объединить через интерактивный rebase. Третья — работа в ветке неделями без синхронизации с main, после чего конфликты занимают больше времени, чем сама задача. Если вы случайно закоммитили пароль или токен, не пытайтесь переписать историю самостоятельно — действуйте по регламенту работы с секретами.
