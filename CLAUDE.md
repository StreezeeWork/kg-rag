# Правила работы в репозитории kb-rag

## Коммиты

- **Важная доработка — сразу коммит.** Как только завершена значимая часть работы (новый модуль
  или функция, исправление бага, изменение данных/метрик, обновление документации), она сразу
  фиксируется отдельным коммитом. Не копить несколько независимых изменений в одном коммите
  и не откладывать коммит «на потом».
- Перед коммитом: `ruff check src tests scripts` и `pytest -q` (для крупных изменений —
  с `KBRAG_RUN_NEURAL=1`); коммитим только зелёное состояние. Если изменение затрагивает данные —
  `kbrag build-gold --check` и `kbrag validate-data`.
- Формат сообщений — Conventional Commits на английском: `feat(scope): ...`, `fix(scope): ...`,
  `docs: ...`, `test: ...`, `refactor: ...`, `chore: ...`, `ci: ...`, `build: ...`.
  Scope — зона проекта: `text`, `ingest`, `retrieval`, `generation`, `pipeline`, `eval`, `api`,
  `cli`, `data`, `config`. В теле — «что и зачем», если это не очевидно из заголовка.
- Один коммит — одна логическая единица; не смешивать, например, правку данных и рефакторинг кода.
- Автор коммитов уже настроен локально (`git config user.name/user.email`, no-reply адрес GitHub);
  глобальный конфиг git не менять.
- Push в `origin` (github.com/StreezeeWork/kg-rag) — после серии связанных коммитов, когда
  тесты зелёные. История `main` не переписывается (без `--force`).

## Окружение

- Проект: `.venv` (CPU, `pip install -e ".[dev,neural]"`). LLM-сервер для локальной генерации:
  отдельное окружение `.venv-llm` (CUDA-сборка torch), запуск — `scripts/serve_local_llm.py`.
- Модели HuggingFace лежат в `D:\workspace\.cache\huggingface` (переменная `HF_HOME`);
  кэш pip — `D:\workspace\.cache\pip`. На диске C мало места — ничего крупного туда не класть.
- Отчёты (`reports/`) в git не попадают; итоговые цифры переносятся в README.
